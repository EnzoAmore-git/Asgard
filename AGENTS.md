# Асгард — короткая инструкция агенту

Основная папка: F:\Проекты\Асгард. Все проекты пользователя хранить в F:\Проекты.
Статус: архитектура v1.0 утверждена. 24.10.2026 пользователь поручил начать фазу 1 подготовки среды по MVP_PLAN.md. Разрешены локальные инструменты и проверки в существующем GitHub Asgard. Beget не трогать до готовности MVP по прямому уточнению пользователя. Следующая фаза — вход и клубы — пока не начата.

## Как читать без лишних токенов
- При старте достаточно этого файла и текущего запроса. Не загружать все документы подряд.
- Найти нужные заголовки через rg, затем прочитать соответствующие разделы и связанные правила.
- Уже прочитанный неизменившийся текст в текущей сессии повторно не читать. После изменения перечитать затронутые части; после потери контекста прочитать эту инструкцию и нужные разделы заново.
- Нельзя экономить за счет пропуска применимых финансовых инвариантов, прав доступа или критериев приемки.

## Какие документы когда открывать
- Назначение, аудитория, MVP, дизайн: PRODUCT_VISION.md.
- Подготовка среды и текущая фаза: MVP_PLAN.md, ENVIRONMENT.md и tools/environment/; GitHub Pages показывает только статические файлы, PHP/MySQL проверяются локально и в GitHub Actions.
- Роли, вход, членство, расписание, явка, уведомления, экраны, Excel: нужный раздел FUNCTIONAL_SPEC.md.
- Архитектура, данные, API, технологии: разделы B–F ARCHITECTURE.md; риски — H; план — I; согласование — J. Полный пересмотр архитектуры требует документа целиком и проверки связанных требований.
- Лендинг: landing/README.md, PRODUCT_VISION.md и связанные разделы FUNCTIONAL_SPEC.md; не подключать базу или авторизацию приложения.
- Любые изменения денег, начислений или влияющей на них явки: FINANCIAL_RULES.md целиком при первом входе в финансовую задачу, затем связанные разделы FUNCTIONAL_SPEC.md и ACCEPTANCE_CRITERIA.md. При изменении правил проверить все затронутые инварианты.
- Реализация модуля после отдельного разрешения: его требования, раздел архитектуры, связанные критерии; правила исполнения — WORKFLOW.md.
- Тестирование/завершение итерации: связанные группы ACCEPTANCE_CRITERIA.md; для релиза — все критерии, для денег — финансовые правила. Не заявлять о неисполненных проверках.
- Beget, PHP, cron, файлы, восстановление: BEGET_HOSTING_CHECK.md и архитектура B/C/H. Для MVP штатные копии, допустима потеря нескольких дней; почасовые копии не требуются.
- Навигация, источники и история переноса: README.md. Правила исполнения/отчетов: WORKFLOW.md. Не читать их при каждом простом вопросе.

## Согласованность
- Не придумывать бизнес-правила и не менять согласованные решения без указания пользователя.
- После нового решения обновить основной документ, связанные критерии и статус; карту менять только при изменении маршрута чтения или этапа.
- Спецификации и историю обсуждения сюда не копировать. Старые инструкции обязательного чтения всего комплекта заменены этой картой по поручению пользователя.
